# Database

MongoDB, through Mongoose. 55 collections; the schemas are in `server/src/models/`.

## Collections

### Access

| Collection | Holds |
| ---------- | ----- |
| `users` | People who can sign in: name, email, password hash, role, department, organization, status, own interface preferences |
| `roles` | A name and a set of permissions. Two are created on first start (full access; default for new users); after that they are ordinary records |
| `permissions` | The catalogue: one document per `<module>.<action>` key, loaded from `seeds/rbac.seed.js` at start |
| `departments`, `organizations` | Where a user works; an organization also owns companies and scopes the dashboard, reports, search and audit log |

### Business records

| Collection | Holds | Belongs to |
| ---------- | ----- | ---------- |
| `companies` | An organisation you deal with | organization, assigned user |
| `contacts` | A person at a company | company |
| `leads` | An enquiry | company?, contact?, source, status, priority, assigned user |
| `opportunities` | A deal in a pipeline | company, contact?, pipeline, stage, lead? |
| `quotations` | An offer: line items and totals | company, contact?, opportunity?, status |
| `orders` | Confirmed business: line items and totals | company, quotation?, status |
| `customers` | A company that has bought (one per company) | company, account manager |
| `projects`, `projecttasks`, `milestones` | Delivery work | company, customer?, order?; task → project |
| `tickets`, `ticketmessages` | Support requests and their conversation | company, contact?, customer? |
| `contracts`, `contractreminders` | Service / maintenance (AMC) contracts; which reminders were sent | company, customer? |
| `payments` | An amount to collect and what was received | company, order? |
| `products` | What is sold | category, unit, tax |
| `activities`, `followups` | Calls, meetings, notes; things to do by a date | any record (`relatedType`, `relatedId`) |
| `documents` | Details of an uploaded file (the file itself is in storage) | any record |
| `timelineevents` | A record's history | any record |
| `notifications` | A message for one user | user, any record |

### Administrator-managed lists

All share one shape (`name`, `description`, `sortOrder`, `isActive`, plus a few
fields of their own) and one set of endpoints:

`leadsources`, `leadstatuses`, `leadpriorities`, `activitytypes`,
`pipelines`, `pipelinestages`, `quotationstatuses`, `orderstatuses`,
`projectstatuses`, `taskstatuses`, `ticketcategories`, `ticketpriorities`,
`ticketstatuses`, `contracttypes`, `contractstatuses`, `billingcycles`,
`contractreminderperiods`, `paymentmethods`, `paymentstatuses`,
`productcategories`, `units`, `taxes`, `industries`, `companytypes`.

A status carries a **category** (for example `open` / `won` / `lost`): the code
depends on the category, never on the name, so names can be changed freely.

### System

| Collection | Holds |
| ---------- | ----- |
| `appsettings`, `companyprofiles` | Application settings and the company's own details (one document each) |
| `auditlogs` | Who changed what, with before and after. Append-only: the model refuses updates and deletes |
| `counters` | The running number of each kind of record |
| `seedstates` | Which first-run lists have been loaded, so they are never loaded twice |

## Relationships

```text
Organization ─┬─ User ── Role ── Permission
              └─ Company ─┬─ Contact
                          ├─ Lead ──(convert)──► Opportunity ── Pipeline / Stage
                          ├─ Opportunity ──► Quotation ──(accept)──► Order
                          ├─ Customer  (created with the company's first order)
                          ├─ Order ──► Project ── Task / Milestone
                          ├─ Order ──► Payment
                          ├─ Ticket ── TicketMessage
                          └─ Contract ── ContractReminder

Any record ── Activity, FollowUp, Document, TimelineEvent, Notification
```

References are ObjectIds. A deleted record is kept (`deletedAt`), so nothing
ever points at a missing document. Deleting is refused while other records
still depend on it (the API answers 409 and lists them).

## Record numbers

`COMP-000001`, `LEAD-000001`, `QUO-…`, `ORD-…` and so on are generated by the
server from `counters` with an atomic increment, are unique, and cannot be
changed. Prefixes are settings; digits are environment variables.

## Indexes

Defined in the models and built at start (`autoIndex`).

| Purpose | Indexes |
| ------- | ------- |
| Uniqueness | `users.email`; every record number; `customers.companyId`; list names; `contractreminders` and `notifications.dedupeKey` (so a job never does its work twice) |
| Filters and joins | Every reference used in a filter: `companyId`, `contactId`, `statusId`, `priorityId`, `assignedTo`, `organizationId`, `pipelineId`, `stageId`, `customerId`, `orderId`, … |
| Dates | `contracts.endDate`, `renewalDate`; `auditlogs.timestamp`; follow-up and payment due dates |
| Global search | `searchKeys` on companies, contacts, leads, opportunities, quotations, orders, projects, tickets, contracts - a begins-with match is answered from this index, never by scanning |
| Lists | `sortOrder` on every administrator-managed list |

List endpoints always page (`page`, `limit`, capped) and sort on the server.

## What is never stored

- Passwords - only a bcrypt hash, excluded from every query by default.
- Access tokens. Of a refresh token only a SHA-256 hash.
- Secrets in the audit log: passwords, tokens and keys are replaced before an entry is written.
- Files: only their details; the bytes are in file storage.
- SMTP and storage credentials: they stay in the environment, never in settings.

## Seeding

| Command | What it loads |
| ------- | ------------- |
| (server start) | The permission catalogue, the two starting roles, and - once - the first values of each list |
| `npm run seed` | The same, without starting the server |
| `npm run create:admin` | The first full-access user (password from `ADMIN_PASSWORD`) |
| `npm run seed:demo` | Demo companies, leads, quotations and so on, for trying the app. **Not for production** |

## Backup and restore

```bash
mongodump   --uri "$MONGODB_URI" --out ./backup-$(date +%F)
mongorestore --uri "$MONGODB_URI" --drop ./backup-2031-01-01
```

Back up the upload folder (or bucket) together with the database: documents
refer to files by their storage key.
